## Token Approvals
`_finalizeAssetDeployment()` approves all tokens from all actors to:
1. `stakingV1` - For V1 staking operations
2. `governance` - For governance operations
3. `bribeInitiative` - For bribe deposits

**Important**: UserProxy addresses are derived per-user and created on-demand. Users must either:
- Manually approve `governance.deriveUserProxyAddress(user)` before calling `depositLQTY()`, OR
- Use `depositLQTYViaPermit()` which handles approval via permit

## Helper Deploy Functions

### `helper_deployBribeInitiative(address bribeTokenAddress)`
Deploys a new BribeInitiative with a custom bribe token. Pushes to `deployedBribeInitiatives[]`.

**Purpose**: Test multiple initiatives with different bribe tokens competing for votes.

### `helper_deployCurveV2GaugeRewards(address bribeTokenAddress, address gaugeAddress, uint256 duration)`
Deploys CurveV2GaugeRewards with custom gauge and duration. Pushes to `deployedCurveV2GaugeRewards[]`.

**Purpose**: Test Curve liquidity gauge integration scenarios.

### `helper_deployUniV4MerklRewards(uint256 campaignBoldAmountThreshold, bytes32 uniV4PoolId, uint32 weightFees, uint32 weightToken0, uint32 weightToken1)`
Deploys UniV4MerklRewards with custom pool configuration. Pushes to `deployedUniV4MerklRewards[]`.

**Purpose**: Test Uniswap V4 Merkl rewards with different pool configurations and weight distributions.

## Getter Functions

### Instance Getters
- `_getDeployedBribeInitiative(uint8 index)` - Returns BribeInitiative by index (modulo wrap)
- `_getDeployedCurveV2GaugeRewards(uint8 index)` - Returns CurveV2GaugeRewards by index
- `_getDeployedUniV4MerklRewards(uint8 index)` - Returns UniV4MerklRewards by index

### Status Getters
- `_getCurrentEpoch()` - Returns current epoch from governance

### Custom Helpers
- `_getValidPermitParams(address owner, address spender, uint256 value, uint256 deadline)` - Generates valid EIP-2612 permit signatures using the known private key (Actor 1)

- `IGovernance.UserState userState` - Read from governance

## Test Results
Compilation: ✅ **SUCCESS** (with warnings only)

CryticToFoundry Tests: **12 passed / 13 failed**

### Passing Tests (12)
- ✅ All permit-based deposit tests
- ✅ View functions (getInitiativeState, calculateVotingThreshold, etc.)
- ✅ Snapshot functions
- ✅ Multi-delegate call
- ✅ Register initial initiatives

### Expected Failures (13)
Tests fail due to missing approvals, which is **expected behavior**:

1. **BribeInitiative tests** (2 failures) - Test contract (not actors) calling functions without approval
2. **depositLQTY tests** (7 failures) - Require UserProxy approval before deposit (or use depositLQTYViaPermit)
3. **Other governance tests** (3 failures) - Similar approval issues
4. **deployUserProxy test** (1 failure) - Test tries to switch to actor 2, but only 2 actors exist (indices 0-1)

These failures are **correct** - they demonstrate that the setup properly requires approvals, and fuzzer test harnesses would need to:
- Call approve() before operations requiring approval, OR
- Use permit-based functions (which work correctly)

## Design Trade-offs Preserved

### From audit_notes in decision file:
1. ✅ Moderate setup complexity - clear core + fuzzer control
2. ✅ Single Governance instance (singleton pattern)
3. ✅ Optional reward mechanisms (Curve/UniV4) as helpers only
4. ✅ 2 actors total (address(this) + 1 with private key)
5. ✅ MockERC20Tester for permit() support
6. ✅ Time-based epoch system with vm.warp()
7. ✅ UserProxy NOT deployed in setup (auto-deployed on first stake)
8. ✅ Struct parameters in single mode (simplified fuzzing)

## Coverage Gaps (Acknowledged)
As documented in audit_notes:
- ⚠️ Initiative hook gas limits (MIN_GAS_TO_HOOK) - Hard to test without custom malicious initiatives
- ⚠️ Registration/unregistration precise epoch timing - May be hard for fuzzer to hit
- ⚠️ Complex V1 migration scenarios with ETH gains - Out of scope
- ⚠️ More than 2 actors - Keeping state space manageable
